# 站点-设备数据模型评估报告

> 评估对象：《数据整理评估.txt》（全站点导出 + 视频站点导出 + 视频设备导出）
> 关联系统：hltgq-mq（MQTT/RabbitMQ 数据入库服务）与 qixiao-apaas 低代码平台
> 结论先行：**当前数据结构已原生支持"一个站点下多个设备"（站点:设备 = 1:N），**
> **问题不在表结构，而在"每个摄像头被建成了一个独立站点"+ 平台侧缺少"多设备"交互。**

---

## 一、背景与客户诉求

客户反馈：**现在每个视频摄像头对应一个站点和一个设备，这样不对**。期望：

1. 一个站点下可以有**多个设备**——譬如一个闸门下同时挂雨量计、水位计和多个摄像头；
2. 站点应支持**选择已有设备**或**新增设备**（设备与站点的绑定关系可维护）。

### 2.2 站点表现状

- 站点总数 360（去重后），`epjutj`（站点类型，多选值 `#N#` 拼接）分布：

  | 类型 | 含义（结合类型字典） | 数量 |

  | `#5#` | 视频点位（本次问题焦点） | **167** |

  | `#2#` | 雨量站 | 16 |
  | `#4#` | 闸门开度 | 15 |

  | 空 | — | 10 |

- **层级关系**：站点表用 `ahieto` 字段自关联父站点 id，层次为
  `花凉亭灌区水库 → 管理所（望江/宿松/太湖/市直/怀宁）→ 枢纽/闸站/渠系/测站 → 视频点位`。

- 其他关键字段：`zzkaec` 站点名称、`iofhpi` 测站编码（**167 个视频站全部为空**）、`devicecode` 设备编码（341 个非空）、`bviiio_x/y` 经纬度、`zebpsu` 启用状态（视频站中 `#1#` 132 个 / `#2#` 35 个，语义待与平台确认）。

### 2.3 设备表现状

- 设备 167 条，全部 `type='#5#'`（视频类），命名统一为 **"{站点名}摄像机#"**；
- `site` 字段 = 绑定的站点 id：**167 条设备绑定 167 个不同站点，每站恰好 1 台设备**；
- 设备 `code` 与所绑站点的 `devicecode` **完全一致（167/167）**，形如 `1000219$1$0$1`：
  - 第 1 段 = 设施/建筑物编码（同一闸门共享，如双庙湖节制闸下的 3 个摄像头均为 `1000219$...`）；
  - 第 4 段 = 该设施下的通道/点位序号（`...$1$0$0`、`...$1$0$1`、`...$1$0$4`）。

### 2.4 问题现状：摄像头 = 1 个站点 + 1 条设备（1:1:1）

每个摄像头在数据上是**一条"视频站点"记录 + 一条"视频设备"记录**。导致：

- 站点树膨胀：360 个站点中 167 个（46%）是视频点位，而非业务监测站点；
- 与真实世界的对应关系被"拍平"：一个闸门下多个摄像头时，表现为**多个"子站点"**而非"一个站点的多个设备"。现网实例（已存在的多摄像头同一设施）：

  | 父站点（真实设施） | 视频子站（=摄像头） | 数量 |
  |---|---|---|
  | 渠首管理所 | 渠首电站上/下游、防洪闸室内、龙谭湖上/泄洪闸… | 12 |
  | 集岭管理所 | 大院内、值班室、安居龙泄洪闸… | 5 |
  | 毕岭管理所 | 章大测流站、太宿进水闸、段垅节制闸… | 5 |
  | 双庙湖节制闸 | 上游、下游、闸室 | 3 |
  | 南山寺/汪元/北干/南干节制闸等 | 上游、下游、闸室 | 3 各 |

  统计：**18 个父站点下挂了 ≥2 个视频站**（其中 1 个父挂 12 个、2 个父挂 5 个）。

## 三、现有系统对该模型的支撑（代码证据）

### 3.1 设备表已在被本服务使用（`MonitorDataService`）

- 设备表 `t_auto_hltgq_water_device` 是本服务的设备档案表；**业务数据行（river_info、gate、pcp_info、soil_data、msg_info 等）同时携带 `site` 与 `device` 两个关联字段**（入库时动态挂接，见 `MonitorDataService#process`）。
- 服务内已有**"一个站点多个设备"的原生机制**（`lookupOrCreateRtuDevice`）：
  - 闸站（epjutj 含 `#4#`）→ 设备"{站点名}1#"，且闸孔可以按闸孔建多个设备；
  - 非闸站已知类型 → 设备"{站点名}+后缀#"：水位计/雨量计/流量计/泵站/墒情探测/水质监测仪；
  - 类型未知 → 兜底"{站点名}待接入#"，后续自动改名自愈（id 不变、数据不迁）。
- `water_device.site` 是普通外键（1:N），**数据上并无"每站仅一设备"的约束**——现状 1:1 只是视频接入侧的建档习惯，不是结构限制。

### 3.2 统计口径已对"视频站"做了防护（`ArrivalStatsService`）

- 参与统计的站点条件：`iofhpi 非空` 且（有设备档案 或 本月有报文流水），或 MQTT 闸站有 gate 数据；剔除测试站。
- 视频站 `iofhpi` 全部为空 → **当前不会污染到报率/缺测率统计**（保持此前提很重要，迁移时不得给视频站补 stcd）。
- 主监测要素映射（`primaryTables`）不识别 `#5#`/`#6#` → 视频点位天然"不参与缺测判定"。

## 四、评估结论

1. **数据结构是否支持"一个站点下多个设备"？——支持。**
   站点表（层级树）与设备表（`site` 1:N）的组合已经具备该能力；本服务的闸站多闸孔设备、多要素设备（水位计/雨量计…）即为运行中的先例。
2. **现状不符客户预期，根因有两层：**
   - 数据组织层：摄像头被建成了**独立站点**（`epjutj='#5#'`），"站点-设备"被迫 1:1；
   - 交互层：平台/前端的站点视图按"站点→单设备"组织，摄像头页面按"视频站点"渲染，缺少"站点下设备列表 + 选择/新增设备"。
3. **因此调整方向不是改表，而是①把摄像头"降级"为业务站点下的设备；②平台补充多设备交互；③稳妥处置存量 167 个视频站点记录。**

---

## 五、调整方案

### 方案 A（推荐）：数据组织调整，不动表结构

1. **设备改挂**：把 167 条视频设备的 `site` 从"视频站 id"改为其**父业务站点 id**（`ahieto` 指向，16 个无父站需人工指定）。
   改挂后：双庙湖节制闸 → 3 台设备（上游/下游/闸室摄像机），直接满足客户"一闸多摄像头"的预期。
   迁移 SQL 示意（**按 id 逐条执行、先备份、可回滚**）：
   ```sql
   -- 备份
   CREATE TABLE bak_water_device_20260920 AS
     SELECT id, name, site, type, status FROM "qixiao-apaas".t_auto_hltgq_water_device;
   -- 单条示例（site 目标值 = 视频站 ahieto 的父站 id）
   UPDATE "qixiao-apaas".t_auto_hltgq_water_device
      SET site = '<父业务站id>', updated_at = now(), updated_by = 'SYSTEM'
    WHERE id = '<设备id>';
   ```
2. **存量视频站处置**（三选一，取决于平台现状）：
   - 保留记录但置停用（`zebpsu`），站点树/下拉不再展示；
   - 平台侧过滤：业务列表统一排除 `epjutj='#5#'` 的站点；
   - 确认无依赖后归档删除。
3. **平台交互**：站点详情页展示**设备列表**（多设备），提供"从现有设备中选择绑定 / 新增设备（写 `water_device`，指定 `site` 与 `type`）"。

### 方案 B：新增"视频点位"子表（仅在视频平台强依赖"站点"结构时考虑）

保持视频站为独立实体，另建 `视频点位` 表挂业务站点+通道号；成本高、改动面大，**不推荐作为第一步**。

### 方案 C（过渡兼容）：新旧并行

- 存量 167 个视频站**暂不动**（保证视频预览页正常）；
- **新接入摄像头一律直接建为业务站点下的设备**（type=`#5#`），不再建视频站；
- 平台多设备交互上线后，再按方案 A 迁移存量。

### 设备命名与编码衔接（已具备）

- 命名："站点名 + 用途 + 摄像机#"（上游/下游区分即可），不与该服务生成的"{站点名}水位计#"等冲突；
- 编码：沿用 `devicecode` 规则（同一设施第 1 段相同、第 4 段为通道序号），便于按段 1 校验"同设施多摄像头"；
- 设备表已有 `ref_type/ref_id` 预留字段（现状全空），如需"设备↔闸孔/视频通道"的强关联可直接启用。

## 六、影响面与风险清单

| 影响点 | 评估 | 动作 |
|---|---|---|
| 视频预览页面 | 若按"`#5#` 站点树"渲染，停用/删除视频站会导致页面异常 | **迁移前与平台/前端确认**；不确定则走方案 C |
| 到报率/缺测统计 | 视频站 `iofhpi` 为空，当前不参与；改挂后设备挂到业务站，业务站本就参与，**口径不受影响** | 迁移后抽查统计站点数不变 |
| 告警/阈值匹配 | 按"站点-设备-类型"匹配，`#5#` 无阈值配置 | 无影响 |
| MQ 数据入库 | 服务按设备**名称**查找/创建（`{站点名}{后缀}#`），与摄像机设备名不冲突；`site` 仅作数据行归属 | 无影响；迁移后勿改设备 name |
| 视频站"启用状态" `zebpsu` | 视频站 `#1#` 132 / `#2#` 35 与普通站（大多 `#2#`）不一致，语义待确认 | 迁移动工前确认 |
| 16 个无父视频站 | 无法自动推导归属设施 | 人工指定父站 |
| 设备表物理约束 | 导出无法确认是否存在唯一索引/触发器 | 执行前查 DDL（`pg_indexes` 等） |
