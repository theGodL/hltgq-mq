- 日期：2026-09-22
- 状态：**已实施（偏移值写死）**；本文件为方案记录与后续升级指引
- 关联文档：`雨量问题排查.md`（34 成因排查全过程）、site 侧《雨量数据异常.md》

- 数据表：`qixiao-apaas.t_auto_hltgq_water_rain_info`（行数据）、`t_auto_hltgq_water_msg_info`（原始报文留痕）

## 一、背景与决策

### 1.1 问题

坝上站（3206400007）站端 9/18 灌数 +34（报文台阶 17.9 → 19.4(+1.5) → 37.4(+18) → 41.9(+4.5) → 51.9(+10)），此后报文持续携带 +34 偏移（当前 52.4 / 52.9 系列同样含偏移）。

- 设备侧修改困难，无法复位/校准 DYP 累计值；
- 此前库外人工"减 34"修正只覆盖到 9/21 12:00，新报文继续以原值入库，修正边界断差 +34 反复导致页面异常（"改了还有"）。

### 1.2 决策

- **由 mq 在入库时做软件补偿**：对 DYP 统一叠加偏移值（当前 -34），落库即为"去偏移"后的真实口径。
- 选择入库层而非展示层补偿的理由：库内数据即刻自洽——站点核心指标、时段降雨派生列（rainfall1h/3h/6h）、各类统计接口、site 展示、对账复核全链路自动一致，无需每个消费方各自处理。
- 阶段规划：**当前写死**（仅坝上站、-34）；后续结合展示端做成**可配置的动态调整值**（第四部分）。

### 1.3 代价与边界（须知晓）

- 补偿后**库内 dyp ≠ 报文原值**（相差 34），这是预期行为；`msg_info` 留痕仍保留原始报文；
- 由此派生一条排查方法论变化：**今后用 msg_info 与 rain_info 对照时，坝上站 diff = -34 属预期补偿，勿判为"人工改数"**；诊断第一步先看补偿日志（见 2.3）。

## 二、当前实现（写死）

### 2.1 代码改动点（MonitorDataService）

| 位置 | 内容 |
| --- | --- |
| `RAIN_DYP_COMPENSATION` 常量 | 写死偏移表：`3206400007 → -34.0`（后续升级为可配置，替代本 Map 即可） |
| `applyRainDypCompensation(...)` | rainInfo 分支中、DYP 守卫之后、`computeRainfall` 之前调用；把补偿后值写回 `fieldMap["dyp"]` |
| `computeRainfall(...)` | 当前 DYP 取值由 `entity["DYP"]` 改为 `fieldMap["dyp"]`（入库值），保证时段降雨与库内同口径 |
| `updateSiteCoreIndicator(...)` | 无需改动：核心指标（ijzsby1）本就读 `fieldMap["dyp"]`，自动同口径 |

**生效链路**：报文 DYP →（补偿 -34）→ fieldMap.dyp → ①落库 dyp ②rainfall1h/3h/6h（当前值-历史值，历史值读库内=补偿后口径）③核心指标 ijzsby1（当前值-水文日基线，基线读库内）。

### 2.2 生效边界

- 仅 `rainInfo` 报文；仅配置站；仅 `DYP` 字段；
- **DRP（日雨量）不参与**：DRP 每日 8:00 重置，与累计偏移无关（花凉亭站 DRP 恒 0 属设备侧字段退化，另行处理）；
- 哨兵值（文本 FFFFFFFF / 4294967295 → 入库 -9991）与缺失值不补偿。

### 2.3 保护与日志

- **补偿后 ≤ 0**：判定设备已复位/偏移变化 → 跳过补偿保留原值，WARN：
  `雨量入库补偿未应用(补偿后≤0, 疑似设备已复位, 请核查并撤除写死补偿): stcd=..., dyp=..., offset=...`
- **正常应用**：INFO：
  `雨量入库补偿已应用: stcd=3206400007, dyp 51.9 -> 17.9 (offset=-34.0)`
- 十进制精确叠加（`addDecimal`），不引入浮点长尾。

## 三、上线配套动作（必做）

### 3.1 历史未修正段一次性修正（9/21 14:10 之后已入库的行）

**必要性**：补偿上线后新行 = 报文-34（如 19.4），与库内旧行（52.4~53.4，未修正）形成 **-34 负跳变** → 时段降雨因负差被忽略不写、核心指标短暂停更（≤6h 窗口）。必须先用一次性 SQL 把历史段拉到与补偿同口径。

**实查清单（2026-09-22 16:24 核查）**：

- 未修正段：**88 行**，tm 2026-09-21 14:10 ~ 09-22 16:00，dyp 52.4 / 52.9 / 53.4；
- 其中 `rainfall3h` 虚高 19 行、`rainfall6h` 虚高 24 行（窗口前值落在已修正段所致）；`rainfall1h` 无需修正（前值均同口径）；
- 核查时**补偿生效性尚未被数据验证**（部署后还没有新报文入库，09-22 16:00 行仍是 53.4）——执行修正前**必须先确认补偿已生效**（见 3.2 第 0 步）。

**SQL 已出稿：`雨量补偿历史段修正.sql`**（同目录），共 4 步：0 核对/前提 → 1 dyp-34 → 2 时段降雨重算 → 3 总验收。要点：

| 列 | 处理 | 说明 |
| --- | --- | --- |
| `dyp` | 统一 -34 | 防重条件 `dyp > 40`（修正后 ≈18~19 不再命中）；上界 `tm < '2026-09-23 00:00:00'` 限定一次性范围（防将来降雨涨值后误重跑） |
| `rainfall1h/3h/6h` | 按修正后 DYP 序列**重算** | 窗口 `[tm-2N, tm-N]` 取最近前值、差值 ∈[0, 上限] 才写（500/1500/3000），与 mq `queryPreviousDyp/computeRainfall` 完全同口径；范围 9/21 14:10 起**无上界**——顺带补"补偿生效后~修正执行前"因负跳变缺列的新行（若存在） |
| 其余列 | 不动 | `drp` 全 0 无偏移；核心指标(ijzsby1)无需 SQL，下一条报文到达时自动按新口径刷新 |

**流程沿用既有约定：SQL 先审核，确认后再执行**（禁止直接执行未审 SQL）。

### 3.2 执行顺序（含前提）

0. **前提：确认补偿已生效**——看库内最新入库行 dyp 是否已是 ≈19.x（补偿后值）。仍是 53.x 说明部署未完成/未重启，先排查（否则修正后新报文继续按 +34 入库，等于白修）；
1. 执行 `雨量补偿历史段修正.sql` 第 0 步核对（存量数量、最新行状态、快照留档）；
2. 第 1 步 dyp 修正 → 第 2 步降雨重算（**顺序不可颠倒**，第 2 步依赖修正后的 dyp；两步均幂等，可重复执行）；
3. 执行第 3 步总验收。

替代序（如需先停服修）：停 mq 容器 → 执行修正 → 部署启动；注意 MonitorData 队列 `x-message-ttl=1h`，停机勿超 1 小时（超时消息会被丢弃）。

### 3.3 验证清单

- [ ] 日志：出现"雨量入库补偿已应用" INFO；无"补偿未应用" WARN；
- [ ] 库内：新行 `dyp = 报文 DYP - 34`；与 msg_info 逐条对照 diff 恒为 -34；
- [ ] 连续性：修正段与补偿段衔接处无 ±34 跳变（SELECT 相邻行差值核对）；
- [ ] 派生列：新行 rainfall1h/3h/6h 数值正常（无 34 级别虚高）；
- [ ] 页面：实时雨情、时段统计接口不再出现 34.0。

## 四、后续升级路径（可配置的动态调整值）

### 4.1 目标形态

结合展示端（业务界面）维护"每站调整值"：可配置、可审计、可即时查看；mq 每次入库按配置应用。**替代当前写死 Map**。

### 4.2 候选方案

| 方案 | 形态 | 生效 | 工作量 | 适用 |
| --- | --- | --- | --- | --- |
| A（轻量） | `application.properties` 仿 `water-level-datum` 模式：`rain-dyp-compensation.offset.<stcd>=-34`，`@ConfigurationProperties` 加载 | 重启生效 | 小时级 | 站点少、变更少、运维可改配置 |
| B（终态·推荐） | 数据库配置表（建议字段：stcd、offset_value、enabled、effective_from、remark、updated_by/at）+ mq 启动加载 + 定时刷新（如 5min） | 免重启 | 天级（含展示端维护界面） | 业务自助维护、按时间段生效、全链路留痕 |

### 4.3 升级触发条件（满足任一即应实施）

- 设备复位后需**按时间段**选择性补偿（需 `effective_from`，写死方案无法表达"某时刻起不再补偿"）；
- 其他站出现同类偏移（写死 Map 可加，但"动态"诉求出现）；
- 偏移值发生变化（不再是精确 34）；
- 业务方要求自助维护（不再依赖发版）。

### 4.4 撤除清单（设备修复/复位后）

1. 确认复位事实：设备复位报文使 dyp 跳回正常小值，补偿将打 WARN（"补偿后≤0"）→ 以 WARN 日志为撤除信号；
2. 撤除/禁用配置：写死阶段改 `RAIN_DYP_COMPENSATION`（删条目）；配置化后 `enabled=0`（推荐）或删条目；
3. 复核库内连续性（衔接处无 ±34 跳变）与报文对照口径；
4. 历史差异处理决议：历史段维持"修正后口径"（推荐）或另议；无论哪种，**本文件变更记录必须同步登记**。

## 五、风险与备忘

- **生命周期依赖人工盯守**：设备一旦复位而配置未撤 → WARN 出现，必须当日处理；建议把"补偿 WARN 监控"纳入日常告警巡检（可复用日志告警）；
- 补偿不涉及：去重逻辑（stcd+tm）、告警阈值判定（用 DRP）、msg_info 留痕；与"已入库数据不可改动"原则不冲突（补偿只作用于写入前的值调整，不改历史行；历史段修正走审核 SQL 单独流程）；
- 与《雨量问题排查.md》的关系：该报告记录的"人工减 34 修正"属于本次补偿上线前的过渡手段，**本方案生效后不再需要人工重复修正**；
- 未来新排查者入口：排查雨量 34 类问题先读本文档第 1.3 节口径备忘。
