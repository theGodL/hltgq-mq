# 数据统计（统计大屏对接文档）

本文档说明统计大屏各模块的数据来源归属：哪些由 hltgq-mq 提供、哪些需要 hltgq-site / hltgq-device 提供，
以及 hltgq-mq 能提供的接口、数据基础和口径，供前后端及跨系统调用方对接。

## 1. 背景与目标

统计大屏包含 5 个模块：

| 模块 | 内容 |
|---|---|
| 站点到报明细 | 站点名称/编号、报文类型（分钟报/整点报）、应到/实到/缺报次数、到报率、状态 |
| 缺测明细 | 站点、缺测时间段、缺测时长、数据类型、当前状态（缺测中/已恢复） |
| 服务监测 | 5 个逻辑服务（数据接收/解析/存储/信息发布/告警推送）的运行状态与资源指标 |
| 数据采集状态统计 | 水位/流量/雨量/闸门开度/视频的应采、实采、成功、失败、成功率 |
| 信息发布情况 | 预计信息的发布次数、成功/失败、成功率、最近发布、状态 |

## 2. hltgq-mq 数据基础（我们能提供的帮助）

hltgq-mq 是全量报文入口：RabbitMQ（每站约 1 小时一批，每批 4 个 tag）+ MQTT（四闸站每 10 分钟一条 payload）
均在本项目完成接收、解析、守卫、入库，因此**"报文字段级"的权威数据都在本项目**。

### 2.1 报文流水 msg_info（到报事实）

`"qixiao-apaas"."t_auto_hltgq_water_msg_info"`：每条报文一行，**守卫前统一留痕**（被拦截的异常报文同样留痕，
如 -999 流量：链路通、设备有上报即算到报）。

| 列 | 语义 |
|---|---|
| site | 站点 ID |
| device | 设备 ID（RabbitMQ=该站 RTU 设备；MQTT=闸孔 1# 设备） |
| stcd | 测站编码（MQTT 无 stcd 留空） |
| tm | 入库时间（服务器时间） |
| sendtm | 设备发送时间（优先报文 SendTM，缺失/异常退业务 TM，再兜底入库时间） |
| afn | 功能码（无则留空） |
| msg | 报文标识（msgInfo 取 MSG 文本，其他 tag 取 tag 名；MQTT 取站点前缀 NSS/QSDZ/QSJSZ/SMH） |
| msg_text | 原始报文 JSON 全文（不加工、不合并） |

### 2.2 业务数据表（有效数据事实）

有效数据按站点类型主监测要素判定（哨兵值 -999/-9991 等不算有效）：

| 数据类型 | 表 | 有效条件 |
|---|---|---|
| 水位 | t_auto_hltgq_water_river_info | `z > 0` |
| 雨量 | t_auto_hltgq_water_rain_info | `dyp > 0`；晴天 DYP=0 不入库，按"该窗有 rainInfo 报文"算有效观测 |
| 流量 | t_auto_hltgq_water_wt_nfo | `q >= 0` |
| 墒情 | t_auto_hltgq_water_nmisp_info | `mten >= 0` |
| 闸门开度/闸站水位 | t_auto_hltgq_water_gate | `up_z > 0 OR down_z > 0 OR open_degree >= 0` |

### 2.3 其他可提供的数据

- 站点档案（站点表 `t_auto_hltgq_5nw74_vnqqef`：站名 zzkaec、stcd iofhpi、类型 epjutj）
- 告警记录（alert 表：失联/超限告警生成在本项目，告警工单联动字段齐全）
- 站点在线/离线状态（基于报文 updated_at 判定，与离线判定同口径）
- 召测能力（POST /api/recall，四站白名单，同步等待应答入库）

## 3. 统计口径（基础定义）

**报到（通信层）**：有报文就算到报。RabbitMQ 站 1 小时窗、MQTT 站 10 分钟窗。

**缺测（数据层）**：有报文但数据有效并入库才算正常，否则缺测；完全没报文也算缺测。
RabbitMQ 站 1 小时窗、MQTT 站 30 分钟窗（对齐 gate 表 30 分钟批量入库节奏）。

**应报/应测窗数**：只统计当日 0 点至当前时刻**已结束的完整窗**（进行中的窗不计，未来时段不摊薄分母）。
到报率 = Σ各站到报窗 ÷ Σ各站应报窗（按站粒度加权）；缺测率同理。

**报文类型**：分钟报 = MQTT 四闸站（南山寺节制闸/渠首电站防洪闸/渠首进水闸/双庙湖节制闸）；
整点报 = RabbitMQ 站。

**参与统计的站点全集**：有 stcd 且（有设备档案 或 本月有报文流水）的遥测站，或有 gate 数据的 MQTT 闸站；
剔除测试站（站名含"测试"或 stcd 以 9999 开头）。新建档未接设备的渠道站不计应报，避免拉低到报率。

**月均口径**：从流水上线日（statStartDate）起逐日平均，跨月后统计窗口跟随本月 1 日；
statStartDate 默认自动取 msg_info 表 msg_text 非空首日，可用配置 `stats.start-date=yyyy-MM-dd` 覆盖。

## 4. 接口清单（hltgq-mq 能实现的）

### 4.1 已实现

**GET /api/report/arrival-stats**（统计卡片聚合）

```json
{
  "code": 0,
  "data": {
    "stationTotal": 86,             // 参与统计的站点总数（已剔除测试站/无设备无流水站，KPI站点总数直接用此值）
    "todayArrivalRate": 92.5,       // 今日到报率(%)
    "monthAvgArrivalRate": 92.5,    // 本月平均到报率(%)，从流水上线日起逐日平均
    "todayMissRate": 7.5,           // 今日缺测率(%)
    "statStartDate": "2026-09-09",  // 本月统计起始日（流水上线日）
    "noReportSites": [              // 今日未到报站点
      { "siteId": "...", "siteName": "周家河", "stcd": "3206400001" }
    ],
    "missedSites": [                // 今日缺测站点
      { "siteId": "...", "siteName": "...", "stcd": "...",
        "lastValidTm": "2026-09-09 08:00:00", "missedWindows": 3, "missRate": 12.5 }
    ]
  }
}
```

结果 60 秒内存缓存（五个接口共享同一统计上下文缓存，高频轮询不重复打库）；错误时 `code=1` 且 `msg` 说明原因。

### 4.2 已实现（四个明细/状态接口）

**GET /api/report/arrival-detail**（站点到报明细，每站一行）

```json
{
  "code": 0,
  "data": [
    { "siteId": "...", "siteName": "周家河", "stcd": "3206400001",
      "msgType": "整点报",      // 分钟报=MQTT四闸站 / 整点报=RabbitMQ站
      "expected": 15,          // 应到次数（今日已结束完整窗数）
      "arrived": 14,           // 实到次数（有报文的窗数）
      "missed": 1,             // 缺报次数
      "arrivalRate": 93.33 }   // 到报率(%)；状态档位（正常/偏低/异常/未到报）由产品定阈值
  ]
}
```

**GET /api/report/miss-detail**（缺测明细，按缺测时间段展开，连续缺测窗合并为一段）

```json
{
  "code": 0,
  "data": [
    { "siteId": "...", "siteName": "...", "stcd": "...",
      "startTm": "2026-09-09 09:00:00",   // 缺测开始时间
      "endTm": "2026-09-09 12:00:00",     // 缺测结束时间（开区间）
      "missMinutes": 180,                  // 缺测时长(分钟)
      "dataTypes": ["水位"],               // 缺测的数据类型（水位/雨量/流量/闸门开度/墒情）
      "status": "缺测中" }                  // 缺测中=覆盖最近完整窗 / 已恢复=已有有效数据
  ]
}
```

**GET /api/report/collect-stats**（数据采集状态统计，按数据类型聚合）

```json
{
  "code": 0,
  "data": [
    { "dataType": "水位数据",
      "expected": 200,       // 应采（采集周期窗数：RabbitMQ 1h / MQTT 30min）
      "collected": 185,      // 实采（有报文的窗数）
      "success": 180,        // 成功（有效数据入库的窗数）
      "failed": 5,           // 失败（有报文但数据无效，如 -999）
      "successRate": 90.0,   // 成功率(%)=成功/应采
      "failRate": 2.5 }      // 失败率(%)=失败/应采
  ]
}
```

维度：水位数据/流量数据/雨量数据/闸门开度/墒情数据（视频归 site/device）；
雨量维度晴天 DYP=0 报文按有效观测计成功。

**GET /api/report/service-status**（mq 自身服务状态；信息发布/告警推送服务由 site 提供）

```json
{
  "code": 0,
  "data": {
    "process": { "startTime": "2026-09-09 08:00:00", "uptimeMinutes": 340,
                 "cpu": 12.5, "memoryUsedMB": 320, "memoryMaxMB": 1024 },
    "services": [
      { "name": "数据接收服务", "status": "运行中", "todayRequests": 350, "successRate": null },
      { "name": "数据解析服务", "status": "运行中", "todayRequests": 350, "successRate": null },
      { "name": "数据存储服务", "status": "运行中", "todayRequests": 220, "successRate": 98.5 }
    ]
  }
}
```

说明：三逻辑服务同进程，进程指标共享；今日请求=今日报文条数（msg_info 行数，MQTT 一条 payload 按 4 站拆 4 行）；
接收/解析环节失败仅 WARN 日志留痕未埋点计数，successRate 为 null；存储成功率为今日有效窗/今日到报窗。

| 模块 | 数据项 | hltgq-mq | hltgq-site | hltgq-device |
|---|---|---|---|---|
| 站点到报明细 | 全部字段 | ✅ | — | — |
| 缺测明细 | 全部字段 | ✅ | — | — |
| 服务监测 | 数据接收/解析/存储服务指标 | ✅（自身进程） | — | — |
| 服务监测 | 信息发布/告警推送服务状态 | ❌ | ✅ | — |
| 服务监测 | CPU/内存/运行时长 | ⚠️ 仅自身进程（JVM） | ⚠️ 仅自身进程 | ⚠️ 仅自身进程 |
| 数据采集状态 | 水位/流量/雨量/闸门开度/墒情 | ✅ | — | — |

| 信息发布情况 | 全部（预计信息） | ❌ 无发布功能 | ✅ | — |

## 6. 需要 hltgq-site 提供

| 数据 | 说明 |
|---|---|
| 信息发布记录 | 发布类型（预计信息）、次数、成功/失败、成功率、最近发布时间、状态（正常/异常） |
| 信息发布服务运行状态 | 运行状态、启动时间、运行时长、CPU、内存、今日请求、成功率 |
| 告警推送服务运行状态 | 同上（告警记录生成在 mq 的 alert 表，可查询；推送环节在 site 侧） |
| 视频数据采集统计 | 应采/实采/成功/失败/成功率（若大华视频平台由 site 对接） |

## 7. 需要 hltgq-device 提供

| 数据 | 说明 |
|---|---|
| 视频数据采集统计 | 应采/实采/成功/失败/成功率（若大华视频平台由设备侧对接，则归 hltgq-device） |
| （可选）设备侧原始状态 | 若需展示传感器故障详情/设备台账等设备原生信息，mq 只能提供报文里已上报的数值 |

> 视频数据归口请按大华平台实际对接位置确定：site 或 device 二选一，mq 均无链路。

## 8. 对接建议

1. **聚合模式**：服务监测页建议"各服务自报指标 + 前端聚合"，mq 只提供自身进程与接收/解析/存储处理量；
   跨服务统一采集 CPU/内存可考虑部署层监控（docker stats / Prometheus），避免各服务实现不一致。
2. **状态阈值归产品**：到报明细的"正常/偏低/异常/未到报"档位由产品定义，mq 提供到报率等原始数字。
3. **查询性能**：msg_info 索引 `(site, tm DESC)`；业务表高频过滤可补 `(site, tm)`。
4. **数据量级**：报文流水约 1800 行/天，业务表约百行/天/表，聚合查询毫秒级，无需离线数仓。
5. **口径一致性**：所有到报/缺测数字统一由 mq 统计接口输出，site/device 不应另起口径（避免大屏数字打架）；
   KPI"站点总数"直接用 arrival-stats 的 stationTotal，不要自行 COUNT 档案表。
