## 一、背景与目标

### 1.1 需求来源

水库上站点需支持**设备巡检**：业主在设备侧手动调整过 34 雨量（坝上站 3206400007 于 9/18 被站端灌数 +34，形成累计雨量 DYP 永久残留偏移，设备暂不具备复位条件），由此衍生两类诉求：

1. **补偿活化**：当前入库减 34 写死在代码（`RAIN_DYP_COMPENSATION`，MonitorDataService L216-219），业主侧调整后无法跟进，需要做成可配置、可随业主操作动态调整的活机制。
2. **问题数据删除**：巡检过程中产生的设备侧异常数据（问题数据行）需要给业主提供历史数据表单，支持业主删除；删除后系统行为必须自洽。

### 1.2 目标效果（需求方表述）

- 给业主**历史数据表单**（可查看、可删除问题数据行）；
- ~~**问题数据删除后，问题数据时间点之后的数据需要更新**（派生列联动重算）~~——**（v1.9，2026-09-28 用户拍板修订：此条取消——"不要修改已生成的数据，对新入库的数据生效即可"）**；
- **后续入库数据需要计算**（新报文使用删除后的序列计算）；
- 补偿参数（如 -34）**实时可调**，不再写死。

## 二、总体设计

### 2.1 角色分工

| 角色 | 职责 |
|---|---|
| 平台（低代码） | rain_info 增加软删列；新建雨量补偿配置表并预置坝上站配置；提供两张表单（补偿配置维护、历史数据管理） |
| mq（本项目） | ①补偿配置化（配置表+缓存）；②入库计算链路软删过滤（v1.9：删除对新入库生效的**唯一落点**）；③列探测降级兼容（~~④软删变更扫描 + 派生列重算任务~~——已随 v1.9 用户拍板取消，历史见 §4.3） |
| site（展示端） | 补偿配置表单、历史数据删除/恢复表单、删除护栏、查询侧软删过滤 |

### 2.2 端到端数据流

```
站端调整(+34残留) ──报文──▶ mq 入库链路
                              │
                              ├─ applyRainDypCompensation：读[配置表缓存]叠加补偿 → dyp 落库
                              ├─ computeRainfall：前值查询[过滤软删行] → rainfall1h/3h/6h
                              └─ computeCurrentRainfall：基线查询[过滤软删行] → 核心指标(下一报文刷新)

业主删除问题行（软删 deleted=true）
      │
      └─ 后续报文：前值/基线查询自动跳过软删行（新入库即按新序列计算——删除的生效方式）

（v1.9 用户拍板）已入库历史行【不重算】——删除点之后的历史派生值保持原样，不做任何回溯修改
```

### 2.3 设计原则

1. **入库唯一计算点（v1.9 修订；原"口径单源"随重算取消自动成立）**：rainfall1h/3h/6h 只在报文入库时计算一次；历史行不回溯——不存在两份实现，口径天然单源；
2. **fail-safe**：任何新机制（配置读取/列探测）失败时降级到"改造前行为"，不中断入库；
3. **不回溯（v1.9，2026-09-28 用户拍板）**：删除/恢复只对**生效时刻之后**的新入库报文生效；已入库行的派生列保持原样（原"软删变更扫描+派生列重算"机制整体取消，历史分析见附二~附十）；
4. **留痕**：软删留 deleted 标记与审计列（deleted_at/deleted_by）；原始报文 msg_info 永不改动；
5. **全站通用（v1.3 澄清）**：软删过滤按 stcd 通用处理，**不设站点白名单**——任何雨量站（含未来新接入站）的删除/恢复自动生效，mq 零改动；补偿配置按站按需（无配置＝无补偿），新站需补偿时表单加一行即 ≤5min 自动生效。

要点：

- **列名契约定案（2026-09-28 用户拍板；R11 关闭）**：**直接在本表新增 `deleted` boolean（NOT NULL DEFAULT false）+ `deleted_at`（状态变更时刻）两列**——一次 DDL、平台侧执行（语句见上）；不走平台 `del_flag` 体系（原"能力问/预置实现约定"分支作废，历史分析见附三~附九）。
  - 分工（v1.9 修订）：`deleted` 供过滤（入库前值/基线）——mq 唯一依赖列；`deleted_at` 供历史管理表单展示"删除时刻/操作人"（原"变更时间窗"机制职责随重算取消）；
  - 平台侧注意：两列为自定义列，**平台自带表单/列表/报表不会自动隐藏已删行**——平台侧直读场景需人工加 `deleted IS NOT TRUE` 过滤（§5.4）；"含已删除"展示由 site 专用表单/接口承载（§5.2）；
  - （v1.9 修订）`deleted_at` 从"机制必需"降为**留痕展示建议**：仍建议与 `deleted` 同批 DDL 加上（表单要如实展示删除时刻）；不加也不影响任何计算正确性（已无降级逻辑）；
- **（已作废·仅存档）del_flag 预置实现约定（v1.6/R30）**：随 2026-09-28 定案失效——原约定（`DEFAULT '#2#'`、未删除/已删除两类谓词拆分、映射常量+启动日志）保留供追溯，实现时忽略；
- **mq 依赖列（v1.2 扩展 R15；v1.9 收敛）**：mq 仅依赖 `deleted`（过滤）——经 `tableColumnsCache` 探测，缺失时过滤自动不拼接、降级为不过滤（启动日志标注）；`deleted_at`/`deleted_by` 为平台留痕展示列（语义＝"最近一次软删状态变更时刻"，删除与恢复均刷新、恢复不清空；v1.9 前 `deleted_at` 曾为时间窗机制依赖，已随重算取消降级）；
  - **deleted_at 建议由服务端（DB）时钟在删除/恢复语句内写入**（`now()`，勿用客户端时间）——避免客户端时钟偏差导致展示时刻失真；
  - 存量行 `deleted_at=NULL` 属正常（历史未发生过状态变更），无需回填；
  - **时间列定案（v1.6 分析；v1.9 修订）**：新增专用"状态变更时刻"列 `deleted_at`（与 `deleted` 同批 DDL）——历史管理表单须如实展示"删除时间/操作人"，借 `updated_at` 会被平台编辑等写入刷新、"何时删/何时恢复"无法如实呈现（结论不变；原"mq 重算刷新"理由随重算取消）；
- `NOT NULL DEFAULT false` 确保存量行与新写入行有确定值；mq 侧仍统一用 `deleted IS NOT TRUE` 写法兼容历史 NULL；
- **软删行保留占位**：行仍在表中（不物理删），重投报文会被去重逻辑挡住，防止"删除行被重投复活"。

## 四、mq 侧改造

### 4.1 补偿配置化（活化）

**改造点**：`MonitorDataService.applyRainDypCompensation`（原 L1684-1705），offset 读取源替换为"补偿配置缓存（device 匹配）"，其余守卫（十进制加、≤0 跳过+WARN、fieldMap.put）全部保留；配套新增 `loadRainAdjustCache`（5min TTL、device 键、三层 fail-safe、失败退避）、`resolveRainCompensationOffset`、`selfCheckDefaultRainStations`（按 stcd 列预置自检）与 `@PostConstruct initRainAdjustCache` 启动预热——**v1.11 已实施（2026-09-28 编译通过）**。

读取三层 fail-safe（v1.1 修订：**必须区分"读取失败"与"读取成功但结果为空"**，site 评审 R04）：

1. **配置表缓存**：启动加载 + 5 分钟 TTL 自动刷新（沿用 `MqttGateDataService.sluiceConfigCache` 先例"页面编辑自动生效"模式）。SQL：`SELECT device, offset_value FROM t_auto_hltgq_water_rain_adjust WHERE enabled = true`，构建 `Map<device, Double>`（v1.11：匹配键=device——以当前入库设备的 device.id 匹配，兼容 MQTT 无 stcd 报文，见 §3.2）。**成功读到空集 = 无补偿**（正常业务结果，如业主已停用/删除全部配置），按空集缓存，不触发任何兜底；
2. **最近成功值**：**仅当本次读取抛异常/失败时**，沿用内存中上次成功的结果 + WARN；
3. **出厂默认兜底**：**仅当"从未成功读过（冷启动）且本次读取失败"时**，启用保留的硬编码默认（现 `RAIN_DYP_COMPENSATION` 更名为 `DEFAULT_RAIN_DYP_COMPENSATION`，注释调整为"出厂兜底，配置表优先"；**兜底按键为 stcd**——坝上站为 RabbitMQ 站必有 stcd，与正常路径的 device 键互不干扰，v1.11）——防止配置表不可用时坝上站裸奔入库 +34 脏数据。**已成功读过空集的进程绝不回退出厂默认**——否则业主停用配置后 -34 会"复活"，与活化目的相反（与 sluiceConfigCache 先例"查无记录是正常业务结果"一致）。

**预置自检（v1.2 新增 R16；v1.4 勘正 R27，逐站判定）**：加载路径对"出厂默认站"（`DEFAULT_RAIN_DYP_COMPENSATION` 的站点集合）**逐一**自检——**该站在配置表中无任何记录（不看 enabled）** → WARN"疑似预置 INSERT 遗漏"（防"成功读空=无补偿"把漏预置静默成坝上站裸奔；多站配置铺开后，其它站有行而本站行被误删同样命中）；有记录但停用 → 属正常业务态，不告警（v1.11：自检按保留的 `stcd` 识别列查询，键设计变更不影响本机制）。

生效时效：表单修改 → 最长 5 分钟（下次刷新）自动生效，无需重启。

### 4.2 软删过滤（入库计算链路）

**共 3 条 SQL、2 个方法**，每条 SQL 追加条件 `AND deleted IS NOT TRUE`（仅当 `tableColumnsCache` 探测到 rain_info 存在 `deleted` 列时拼接；探测缺失=自动降级为不过滤+启动日志标注）：

| # | 方法 | SQL 位置 | 追加条件后效果 |
|---|---|---|---|
| 1 | `queryPreviousDyp`（L1783-1812）device 非空分支 | L1790-1792 | 前值窗口跳过软删行，取窗口内其余更早行 |
| 2 | `queryPreviousDyp` device 为空分支 | L1795-1797 | 同上 |
| 3 | `queryHydroDayBaseDyp`（L2185-2201） | L2190-2192 | 水文日基线跳过软删行（基线被删则自动前移） |

说明：

- 这两处正是"**后续入库数据需要计算**"的落点：删除后下一报文起，前值与基线天然使用删除后的序列（v1.9：这也是删除的**唯一生效方式**——已入库历史行不重算）；
- 前值守卫（`prev > 0 && prev != SENSOR_COMM_ERR`，L1803）与差值上限守卫（500/1500/3000，L165-167）不动；
- 窗口**不扩展**（仍为 [tm-2N, tm-N]）：窗口内无合法行时按现行口径不写列（新行为 NULL）；

#### 4.3.2 触发机制（软删行集差 + 变更时间窗 + 受影响区间）

> v1.1 设计修订（site 评审 R01/R02/R05）：以"**内存软删行集合 vs 本轮扫描集合的对称差**"替代聚合指纹，一次消解四类问题——①恢复最后一条后站点从结果集消失→不触发（R01）；②恢复最早行后起点后移→漏算受影响区间（R02）；③聚合特征碰撞（恢复+删除组合）；④"最早删行起全段"范围随软删累积无界增长（R05）。
> v1.2 修订（site 二轮评审 R15）：补"**变更时间窗**"——消解"删除与恢复落在相邻两轮扫描之间（<5min，误删立即撤销的主场景）且期间有报文入库"时 cur==memory、差集为空、漏重算的竞态：site 侧删除/恢复均把 `deleted_at` 刷新为变更时刻，mq 除软删全集外一并捕获"近期有变更痕迹的行"。
> v1.3 修订（site 三轮评审 R21/R22）：①时间窗取消 `deleted=false` 限定——被 `deleted_at > 水位` 捕获的行**全量纳入变化集（不分 deleted 值）**，消解"同一间隔内删→恢复→再删（终态=删除=内存态）"净零闪断漏重算（集差首终态一致为空、旧限定又把该行排除）；②明确分站水位与扫描 SQL 的衔接及 deleted_at 写入时钟要求（见下）。

- **调度**：独立任务类（建议 `RainRecomputeService`），`@Scheduled(fixedDelay=300000)` 每 5 分钟，首轮 `initialDelay` 30s；
- **每轮扫描**（分站水位＝该站已处理变更痕迹的最大 `deleted_at`；冷启动＝now-24h 一次性回退窗口；软删全集分支由部分索引 idx_rain_deleted 支撑）：

```sql
-- 变更捕获：软删全集（集差用） + 近期变更痕迹（时间窗用）
-- 下界：floor = min(各站水位的全局最小值, now()-24h)——now()-24h 常量恒定参与取小（R28：
-- 保证"未建水位的新站按冷启动 now-24h"在 SQL 层真正成立）；安全性优先多取；
-- Java 内再按分站 deleted_at > watermark[stcd] 精确过滤（R22①：勿做成全局单水位，
-- 否则 A 站成功推进会越过 B 站失败未处理的痕迹、丢失 B 站重试语义）
SELECT stcd, tm, deleted, deleted_at FROM "qixiao-apaas".t_auto_hltgq_water_rain_info
WHERE deleted IS TRUE OR deleted_at > :watermark_floor;   -- 严格 > 配水位=max(deleted_at)：不重复、不漏边界
```

> （已作废·仅存档）del_flag 分支映射（v1.7，R30）：随 2026-09-28 定案（直接加 `deleted` boolean）失效，扫描 SQL 按上方原文执行；原映射注记保留供追溯。

- **变化行集** = ①**集差**：`symDiff(内存软删集, 本轮 deleted=true 行)`（新增删除 ∪ 恢复；R01 场景恢复最后一条差集仍非空必触发）∪ ②**时间窗**：本轮被 `deleted_at > 水位` 捕获的行——**全量纳入、不分 deleted 值**（v1.3 修订 R21：不再限定 deleted=false；稳态软删行 deleted_at ≤ 水位 不会重复触发，单调水位已兜住；重复捕获幂等无害）；
  - R15 场景验证：X 删除与恢复均落在两轮之间、期间报文 Y 按"X 已删序列"自算 → 恢复后 X 不在内存（从未被记录）但 X.deleted_at=恢复时刻 > 水位 → 时间窗捕获 → 区间 [X, X+12h] ∋ Y → Y 修复；
  - R21 场景验证：X 先已软删（在内存软删集中）→ 同间隔内 恢复→再删（终态=删除=内存态）：集差 ∅，但 X.deleted_at=末次删除时刻 > 水位 → 时间窗捕获 → 恢复窗口（X 可见期间）入库的 Y（按含 X 序列自算）被 [X, X+12h] 重算修复；
- **重算区间**：变化行集内每个行 `y` 生成 `[y.tm, y.tm+12h]`（12h＝6h 窗口上界 2N，且**含被恢复行自身**——其派生列在软删期间未重算，恢复后需补算），重叠/相邻合并，终点截断到扫描时刻快照；**区间外行一律不动** → 单轮重算量恒为"变化点后 12h"，不随软删行累积增长；
  - R02 修复验证：旧 {9/1 10:00, 9/28 10:00}，恢复 9/1 → 差集={9/1} → 区间 [9/1, 9/1+12h] ✓；
- **内存/水位推进（分站）**：仅当该站全部区间重算成功后——内存＝本轮 `deleted=true` 集合；水位＝本轮该站捕获行**非 NULL** 的 `max(deleted_at)`（捕获集为空或全为 NULL 则水位不动，防 NULL 水位令比较恒 UNKNOWN、时间窗失效，R24）；任一失败保留旧内存与旧水位（下轮重算、幂等重试）；
- **重启安全**：内存/水位丢失 → 水位=now-24h → 捕获"当前软删全集 + 近 24h 变更痕迹"重算一次（幂等无害）；
- **降级**：`deleted_at` 缺失（探测）时退化为纯集差（v1.1 行为），启动 WARN"竞态防护未启用"（残余：两轮扫描之间的**净零变更**——删→恢复、或删→恢复→再删（终态与内存一致）——且期间有入库时不触发，对该行"再删一次→恢复"即可强制触发重算）；
- **并发隔离**：区间终点限定"扫描时刻已存在的行"（tm 快照），不触碰重算期间新入库的行；新行由入库链路自算且前值已过滤软删，两条路径无冲突；
- **日志**：每轮记录 INFO（站、差集/时间窗行数、区间、扫描行数、实际更新行数），异常 WARN；
- **单实例假设**：当前单容器部署无需分布式锁；若未来多实例部署需加重算互斥。

#### 4.3.3 伪代码

```
每 5 分钟（分站水位 watermark[stcd]，初始 now-24h）：
  cap = SELECT stcd, tm, deleted, deleted_at FROM rain_info
        WHERE deleted IS TRUE OR deleted_at > floor            // floor=min(全站水位, now-24h)；Java 内按分站过滤（R22①/R28）
  for stcd in (memory.keySet() ∪ cap 键集):
     diff = symDiff(memory[stcd], {cap 中该站 deleted=true 的 tm})  // 集差：新增删除 ∪ 恢复（tm 毫秒 long）
     diff ∪= {cap 中该站 deleted_at > watermark[stcd] 的行}          // 时间窗：近期变更痕迹全量（不分 deleted；R21）
     if diff.isEmpty: continue
     intervals = merge([ [y, y+12h] for y in diff ])             // 区间合并，截断到扫描快照
     ok = true
     for [from,to] in intervals:
        rows = SELECT * FROM rain_info
               WHERE stcd=? AND tm >= from AND tm <= to
                 AND deleted IS NOT TRUE                          // 加固①：排除软删行本身
               ORDER BY tm
        for r in rows:
           try:
              {r1,r3,r6} = calcRainfallColumns(stcd, r.device, r.tm, r.dyp)  // 与入库同款
              逐列比较：新有效值与现值不同（含现值 NULL）才写该列（R17 统一）
              任一列实际变化 → UPDATE 该行＋审计列 SOFT_RECOMPUTE
           catch e: ok=false; WARN                                // 加固②：行级隔离，本站整体视为失败
     if ok:
        memory[stcd] = {cap 中该站 deleted=true 的 tm}
        watermark[stcd] = max(cap 中该站行非 NULL 的 deleted_at)  // 分站推进；集空/全 NULL 则不动（R15/R24）
```

实现加固（site 评审 R14/R15/R21/R22/R24/R28）：①区间行查询排除软删行本身（软删期间不更新不可见行；恢复后由其自身区间触发补算）；②行级 try/catch 隔离，单行失败不中断区间，但该站本轮不推进内存/水位（下轮整体重算、幂等重试）；③集差与水位比较用毫秒 long（消除浮点比较问题）；④时间窗条件用严格 `>` 配"水位=max(deleted_at)"——不重复、不漏边界；⑤**deleted_at 写入必须用服务端（DB）时钟**（单调捕获推理的前提，R22②），扫描 SQL 下界 floor=min(各站水位, now()-24h)（R28）、Java 内按分站过滤（勿做全局单水位，R22①）；⑥水位推进取捕获集**非 NULL** 的 max(deleted_at)，捕获集为空或全 NULL 时水位不动（防 NULL 水位使时间窗永久失效，R24）。

## 六、边界与口径说明（业务必读）

1. **删除不消除设备侧跳变**：若业主删的行恰为设备累计的跳变点（如灌数上跳行），其**后续新报文**的差值会跨越跳变（呈现跳变量）——这是设备事实，删除只删观测、不改变累计。当前库内序列已修正连续，正常不会发生。
2. **告警不追溯撤销**：删除前已按当时数据产生的阈值告警**保留为历史记录**，不因删除而撤销。
3. **到报统计不受删除影响**：到报率/联通率按通信事实统计，软删行仍计入到报（软删行保留占位）。
4. **msg_info 永不动**：原始报文流水不随删除变化；对照核验时 rain_info 与 msg_info 的 dyp 相差 -34（坝上站）属预期。
5. **站表核心指标刷新时点**：删除后指标**不立即变化**（v1.9 无重算）；下一报文到达时自动按删除后序列刷新（已拍板口径）。站停报期间指标可能短暂保留旧值（失联巡检 24h 置 0 机制兜底展示）；**刷新量级（v1.1，site 评审补充）**：等于该站正常上报节奏——灌区站约 20min、水文站约 4h，"删除后大屏多久更新"请按此对齐需求方预期。**"不回溯"范围（R34 补充）**：v1.9 的"不回溯"仅指 **mq 存储的派生列（rainfall1h/3h/6h）与站表核心指标**；**site 页面自算值**（gq-rainfall 列表/大屏等按 dyp 现算 + 查询过滤）在 site 侧过滤上线后**随删除即时变化**（被删行消失、邻近时段值即时变化，对应验收 #8）——两者预期不同、互不矛盾（防联调把"页面变了"误判为"历史被回溯修改"）。
6. **空列展示与"算不出"（v1.1 显式化 R07；v1.9 重写——重算取消后口径消解）**：**新增行**若窗口内无合法前值 → 列为 NULL（口径"不写入"）。**"算不出"的根因与现状量级（v1.8，回应 2026-09-28 质询）**：前值必须落在**滞后窗口**——rainfall1h→[tm-2h, tm-1h]、3h→[tm-6h, tm-3h]、6h→[tm-12h, tm-6h]（`queryPreviousDyp` 实码）；窗口内只取**最近一条**且须 dyp>0 非哨兵，不合格直接放弃（**不回溯**更早行）——窗口为空或候选不合格即"算不出"。这不是理论边角：**现状（无任何删除）**全表 32366 行中 rainfall1h 已有 8507 行（26%）为 NULL、3h 3992 行、6h 3783 行；稀疏站（约 3h 上报一条）rainfall1h 约 85% 为 NULL（只读核查 2026-09-28）。**（v1.9 用户拍板）已入库行不重算**：删除/恢复不改动任何历史派生值——原"历史行重算算不出时保留原值 vs 置空"的抉择随重算取消自动消解（一律保持原样）；被删行对其后已入库值的残余影响可能仍在（业务已明确接受"只对新入库生效"；原 site 展示面盘点、两策略理由与话术存档见附七/附九）。
7. **展示端不显示已删行**：除非历史管理表单开启"含已删除"视图。
8. **补偿操作约定**：设备侧复位/再次调整前，先在补偿配置表单停用或更新 offset，避免过渡窗口错补。
9. **补偿值变更/设备复位的存量联动（v1.1 新增，site 评审 R09；v1.9 微调）**：offset 变更或设备复位属于"**口径切换动作**"——切换点前后 dyp 序列若存在断差，修复的关键是**对存量 dyp 做一次性修正**（先例：《雨量补偿历史段修正.sql》，含随后的 rainfall 重算）——本方案（v1.9 后）不含任何存量重算/修正机制。操作手册约定：任何 offset 变更/设备复位前，先评估存量数据是否需要配套修正流程；复位后"值>34"突变自动检测列入二期。
10. **误删恢复的效果边界（v1.2 新增 R15；v1.9 重写——重算取消）**：误删后恢复，**后续新报文**即按恢复后的完整序列计算，无需人工干预；但**删除期间入库的报文不回补修正**（其派生值按当时"已删序列"算出，保持原样）——如确需修正该窗口，属人工存量修正范畴（先例：《雨量补偿历史段修正.sql》）。同理，删除本身也不回溯：删除点之后已入库行中可能残留被删行参与的影响（业务已明确接受"只对新入库生效"，v1.9 拍板）。
