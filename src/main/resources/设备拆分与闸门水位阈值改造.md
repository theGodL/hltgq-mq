# 设备按传感器拆分 与 闸前/闸后水位阈值改造

> 编写：2026-10-26　对象：hltgq-mq 维护方
> 依据：对生产库 `qixiao-apaas`（172.27.177.30）的只读核对 + 两端源码比对
> 本文两件事互相独立，可分两期上线，顺序见第五节

---

## 一、背景

两件事需要 mq 侧配合：

1. **设备粒度错误**：设备档案按"上报终端（RTU）"建，一台设备同时挂水位、流量、雨量、闸门。硬件实况是一台传感器一种数据，业务侧设备名也只反映其中一个类型（如"虎形潭渡槽流量计#"实际还在上报水位）。需要 mq 按数据类型把数据写到对应传感器的设备上。
2. **闸前/闸后水位阈值不兼容**：hltgq-site 的阈值设置已支持闸站按 `up_z`（闸前）/`down_z`（闸后）分别配置，mq 告警引擎仍按"单指标"查询，导致两行阈值被任意取一行判定。

---

## 二、问题一：设备按传感器拆分

### 2.1 现状数据（只读实测）

设备表 465 台，其中**实际采集 2 类以上监测数据的有 42 台**：

| 组合 | 台数 | 代表 |
|---|---|---|
| 水位 + 流量 | 3 | 虎形潭渡槽流量计#（水位 11343 + 流量 11400）、双庙湖渡槽流量计#（307+312）、夏家湖渡槽流量计#（230+230） |
| 水位 + 雨量 | 13 | 周家河水位计#（17208+4873）、花凉亭坝上水位计#（10436+7766）、花凉亭坝下水位计#（4374+3884）、10 台雨量计# |
| 流量 + 闸门 | 26 | 渠首进水闸1#（闸门 8386 + 流量 5645）、南山寺节制闸1#（8416+4337）等 |

设备 `type` 多值（`#3#|#5#|#6#|#1#` 这类）只有 5 台，但**实际采多类的有 42 台**——说明多值只是偶然抄对了。

> **业务口径（业主明确，2026-10-26）**：每台设备只能有一个监测类型，功能页面一律按单值使用、禁止多选。数据库列保留多选配置（`#ENUM_MULTI#`）是平台模型层的既有设定，不动它只为避免改动平台结构引发连带问题，**不代表允许一台设备挂多个类型**。拆分是既定方向，不是可选方案。

### 2.2 根因（三处）

**根因一：缓存键是 stcd，一个站号只对应一台设备**

`MonitorDataService` 字段声明：

```java
/** stcd → 主设备 device_id 缓存（闸站=闸孔1，非闸站=RTU设备） */
private final ConcurrentMap<String, String> stcdDeviceCache = new ConcurrentHashMap<>();
```

入库主流程（`MonitorDataService#handleMessage`，构建 `fieldMap` 处）：

```java
if (isValidColumn(validColumns, "device")) {
    String device = lookupOrCreateRtuDevice(stcd, site);   // ← 所有 tag 共用同一台设备
    if (device == null) { ... return; }
    fieldMap.put("device", device);
    markDeviceOnline(device);
}
```

`tag` 决定写哪张表（`TAG_TABLE_MAP`），但 `device` 只有一个。所以 `wtInfo`、`riverInfo`、`rainInfo` 无论写哪张表，`device` 列都是同一个 id。

**根因二：设备命名按站点主类型，不按数据类型**

`MonitorDataService#lookupOrCreateRtuDevice`：

```java
// 闸站(#4#): 统一用闸孔1设备
if (epjutj != null && epjutj.contains("#4#")) {
    deviceName = siteName + "1#";
    deviceType = "#4#";
} else {
    String suffix = SITE_TYPE_DEVICE_MAP.get(extractPrimarySiteType(epjutj));
    deviceName = siteName + suffix + "#";
    ...
}
```

`SITE_TYPE_DEVICE_MAP` 只有 1/2/3/6/7/8（水位计/雨量计/流量计/泵站/墒情探测/水质监测仪），**没有 4 和 5**；主类型码只取 `epjutj` 里第一个 `#N#`。

**根因三：设备 type 直接抄站点 epjutj**

```java
String suffix = SITE_TYPE_DEVICE_MAP.get(extractPrimarySiteType(epjutj));
deviceType = epjutj;   // ← 如 "#3#|#5#|#6#|#1#" 整串写入设备 type
```

站点 `epjutj` 是多值（站点确实可以有多类监测能力），但设备不该继承整串。这是设备 type 出现多值的唯一来源。

**附带现象**：由于 `stcdDeviceCache` 一旦建立就不刷新，站点档案后补 `#4#` 时缓存仍指向早期设备，导致现网同时存在两种形态——90+ 站已经是 `{站名}流量计#`（#3#）+ `{站名}1#`（#4#）共存，26 站的 `{站名}1#` 仍同时挂流量和闸门。**这不是设计，是缓存时序差异。**

### 2.3 目标模型

**一台物理传感器 = 一条设备档案 = 单一 type。**

> 平台模型里 `type` 列是 `#ENUM_MULTI#`（多选枚举），本次不改模型、不改列配置。但 mq 写入只写一个类型码：功能页面（视频清单 `type LIKE '%#5#%'`、站点设备按类型筛选、设备总览分类统计）都按单值语义使用，写多值会让同一台设备同时出现在多个分类里，也会让「设备类型」字段失去可读性。

报文 tag → 设备类型映射：

| 报文 tag | 入库表 | 设备 type | 设备名后缀 | 说明 |
|---|---|---|---|---|
| `riverInfo`（Z 有值） | river_info | `#1#` | 水位计 | 通用水位 |
| `riverInfo`（Z 无值，Z1/Z2） | gate（up_z/down_z） | `#4#` | `1#` | 闸站水位，跟闸孔1设备 |
| `wtInfo` | wt_nfo | `#3#` | 流量计 | 瞬时流量 Q |
| `rainInfo` | rain_info | `#2#` | 雨量计 | 日雨量 DRP / 累计 DYP |
| `gatesInfo` / `gateInfo` | gate | `#4#` | `{闸孔号}#` | 闸门开度 |
| `soilData` | soil_data | `#7#` | 墒情探测 | 三层含水率 |
| `pcpInfo` / `nmIspInfo` | pcp_info / nmisp_info | `#8#` | 水质监测仪 | 理化+水质七项 |
| `volInfo` | vol_info | 不单独建档 | — | RTU 自身电压，非传感器 |
| `msgInfo` | msg_info | 不单独建档 | — | 报文流水，`device` 留空或挂主设备 |

> `volInfo` / `msgInfo` 是终端级报文，不产生独立传感器。建议 `device` 留空（两表列可空即可），或挂该站主设备，二选一但要在代码里写死，不要"取第一个非空"这种隐式规则。

### 2.4 改造清单

#### 改动 1：设备解析按 tag 分流

新增 tag → 设备后缀映射（替换现有 `SITE_TYPE_DEVICE_MAP` 在入库主链路的用途）：

```java
/** 报文 tag → 传感器设备名称后缀（只覆盖传感器类 tag；闸门走既有闸孔逻辑） */
private static final Map<String, String> TAG_DEVICE_SUFFIX = new LinkedHashMap<>();
static {
    TAG_DEVICE_SUFFIX.put("riverInfo", "水位计");
    TAG_DEVICE_SUFFIX.put("wtInfo",    "流量计");
    TAG_DEVICE_SUFFIX.put("rainInfo",  "雨量计");
    TAG_DEVICE_SUFFIX.put("soilData",  "墒情探测");
    TAG_DEVICE_SUFFIX.put("pcpInfo",   "水质监测仪");
    TAG_DEVICE_SUFFIX.put("nmIspInfo", "水质监测仪");
}

/** 报文 tag → 传感器设备 type（单一值，禁止多值） */
private static final Map<String, String> TAG_DEVICE_TYPE = new LinkedHashMap<>();
static {
    TAG_DEVICE_TYPE.put("riverInfo", "#1#");
    TAG_DEVICE_TYPE.put("wtInfo",    "#3#");
    TAG_DEVICE_TYPE.put("rainInfo",  "#2#");
    TAG_DEVICE_TYPE.put("soilData",  "#7#");
    TAG_DEVICE_TYPE.put("pcpInfo",   "#8#");
    TAG_DEVICE_TYPE.put("nmIspInfo", "#8#");
}
```

缓存键从 `stcd` 改为 `stcd|tag`：

```java
/** stcd|tag → 该传感器设备 id（原 stcdDeviceCache 的替代） */
private final ConcurrentMap<String, String> stcdTagDeviceCache = new ConcurrentHashMap<>();
```

新增解析方法（`lookupOrCreateRtuDevice` 保留给 `volInfo`/`msgInfo` 兜底，或直接废弃）：

```java
private String resolveDeviceByTag(String stcd, String siteId, String tag) {
    String suffix = TAG_DEVICE_SUFFIX.get(tag);
    if (suffix == null) {
        return null;   // volInfo / msgInfo：不挂设备
    }
    return stcdTagDeviceCache.computeIfAbsent(stcd + "|" + tag, k ->
            lookupOrCreateDeviceByName(getSiteName(siteId) + suffix + "#",
                                       siteId, TAG_DEVICE_TYPE.get(tag)));
}
```

调用侧（`handleMessage`）：

```java
if (isValidColumn(validColumns, "device")) {
    String device = resolveDeviceByTag(stcd, site, tag);   // ← 按 tag 取
    if (device != null) {
        fieldMap.put("device", device);
        markDeviceOnline(device);
    }
}
```

**闸站 riverInfo 例外**：`Z` 无值（闸前/闸后水位）时走 `insertGateWaterLevelFromRiverInfo`，那里已有独立的闸孔设备查找（`siteName + "1#"`, type `#4#`），**保持不动**。改造只处理"Z 有值"及非闸站分支。

#### 改动 2：设备 type 不再抄 epjutj

`lookupOrCreateDeviceByName(name, siteId, type)` 的 `type` 参数只允许传单一类型码（数据库列保持多选配置不动，只是写入单值）。原 `lookupOrCreateRtuDevice` 里的 `deviceType = epjutj` 必须删除。

顺带清理存量：42 台设备的 type 需改为单一值（见第六节清单）。

#### 改动 3：markDeviceOnline 按传感器粒度

现状："收到任一报文就把该 stcd 的设备标在线"。拆分后若沿用，会出现**水位计三个月没上报但显示在线**（因为流量计还在报）。

改法：`markDeviceOnline(device)` 只标记本次报文命中的设备（改动 1 已经天然做到，注意不要回退成按 stcd 标记）。

#### 改动 4：闸站流量迁到独立流量计设备

26 个闸站的 `{站名}1#` 同时挂闸门 + 流量。改后：

- `{站名}1#`（type `#4#`）只写 `gate` 表
- `{站名}流量计#`（type `#3#`）写 `wt_nfo`

**注意**：现网 90+ 站已有 `{站名}流量计#` 设备（历史缓存造成），改造后这些站自动归位，无需额外处理；26 站需新建流量计设备并迁移历史流量数据（见 2.5）。

#### 改动 5：告警 device 跟随传感器

`alertService.evaluateThreshold(site, deviceId, ...)`、`reportDeviceError(...)` 的 `deviceId` 改为本次报文命中的传感器设备 id。告警挂到具体传感器上，前端"设备名称"列才准确。

### 2.5 历史数据迁移

**顺序**：先上线 mq（新数据按新逻辑写）→ 再迁历史。反过来会导致 mq 继续写回旧设备。

**第一步：建缺失的传感器设备**

按第六节清单，为每台待拆设备补齐第二（三）类型设备。示例（虎形潭渡槽）：

```sql
INSERT INTO "qixiao-apaas"."t_auto_hltgq_water_device"
  (id, corp_code, created_at, created_by, updated_at, updated_by, name, site, type)
SELECT '<新水位计id>', 'hltgq', now(), 'SYSTEM', now(), 'SYSTEM',
       '虎形潭渡槽水位计#', d.site, '#1#'
FROM "qixiao-apaas"."t_auto_hltgq_water_device" d
WHERE d.id = '<原流量计id>';
```

设备 id 用 20 位（与 `IdGenerator` 一致），建议由低代码后台新建以保证 id 规则一致，或由 mq 首次收到报文时自动建（改造后会自动建，可省去手工 INSERT）。

**推荐做法**：不手工 INSERT，直接上线 mq，让 `resolveDeviceByTag` 首次收到报文时自动建，然后按"名称 + site"回填历史数据的 device。

**第二步：历史数据按 tag 归位**

```sql
-- 水位数据迁到水位计设备（示例：虎形潭渡槽）
UPDATE "qixiao-apaas".t_auto_hltgq_water_river_info
   SET device = '<水位计id>'
 WHERE device = '<原流量计id>';

-- 流量数据迁到流量计设备（示例：渠首进水闸 1# 上的流量）
UPDATE "qixiao-apaas"."t_auto_hltgq_water_wt_nfo"
   SET device = '<流量计id>'
 WHERE device = '<渠首进水闸1#id>';
```

**迁移量实测**（42 台设备口径）：

| 表 | 待迁行数 |
|---|---|
| `t_auto_hltgq_water_river_info` | 18,097 |
| `t_auto_hltgq_water_wt_nfo` | 57,882 |
| `t_auto_hltgq_water_rain_info` | 8,757 |
| `t_auto_hltgq_water_gate` | 0（闸门数据本来就挂在 #4# 设备上，正确） |

总计约 8.5 万行。`rain_info` 有 `deleted` 列，迁移时不要过滤软删行（一并迁，保持历史完整）。

### 2.6 灰度开关与回滚

建议加配置开关（新配置项，默认关闭）：

```properties
# 设备按传感器拆分：true=按报文类型写对应传感器设备；false=旧逻辑（stcd 单设备）
app.device-split-enabled=false
```

- 关闭时走原 `lookupOrCreateRtuDevice`，行为与现网一致
- 开启后新数据写传感器设备，旧设备保留历史数据不删
- **回滚**：开关置回 false 即可（新数据回到主设备，已迁移的历史数据不用回滚，只是设备归属不一致，不影响展示——网站按 `site`/`STCD` 取数）

### 3.2 改造清单

#### 改动 1：调用侧显式传指标

`MonitorDataService` 六处调用：

```java
// ① 通用水位（riverInfo Z 有值）— 显式传空串，只匹配 zb 为空的行
alertService.evaluateThreshold(site, deviceId, AlertService.TYPE_WATER_LEVEL,

// ② 流量（wtInfo）
alertService.evaluateThreshold(site, deviceId, AlertService.TYPE_FLOW,
        siteName, "流量", "", q, bizTm);

// ③ 雨量（rainInfo）
alertService.evaluateThreshold(site, deviceId, AlertService.TYPE_RAINFALL,
        siteName, "雨量", "", currentRain, bizTm);

alertService.evaluateThreshold(siteId, device, AlertService.TYPE_WATER_LEVEL,

// ⑤ 闸后水位（insertGateWaterLevelFromRiverInfo）

        siteName, "闸后水位", "down_z", z2, tm);

```

墒情（`#7#`）与水质（`#8#`）走 `evaluateThresholdBatch`，`zb` 已经是列名，无需改。

#### 改动 2：findThreshold 语义收紧

**`null` 不再表示"不限定指标"，而是"指标为空"**，防止将来漏传又退化成串用：

```java
private Map<String, Object> findThreshold(String siteId, String typeCode, String zb) {
    try {
        String sql = "SELECT threshold, alarmdir FROM " + THRESHOLD_TABLE +
                " WHERE \"site\" = ? AND COALESCE(NULLIF(\"zvieyb\", ''), \"type\", '') LIKE CONCAT('%', ?, '%')" +
                " AND COALESCE(NULLIF(\"zb\", ''), '') = ?" +
                " LIMIT 1";
        List<Map<String, Object>> rows = jdbcTemplate.queryForList(sql, siteId, typeCode,
                zb == null ? "" : zb.trim());
        return rows.isEmpty() ? null : rows.get(0);
    } catch (Exception e) {
        log.warn("查询阈值配置失败, site={}, type={}, zb={}: {}", siteId, typeCode, zb, e.getMessage());
        return QUERY_FAILED;
    }
}
```

`findThresholdRows`（批量用）已经按 `zb` 建映射，键为空串表示通用，**无需改**。

#### 改动 3：注释与文案口径同步

- `evaluateThreshold` 的 5 参重载注释"（水位/雨量/流量/开度/闸站水位等，zb 恒为空）"已过时，改为"单指标类型调用请用 6 参显式传 zb（通用指标传空串）"
- `unitFor`：`#1#` 已返回 `m`，闸前/闸后同为 m，**无需改**
- `isBelowByDefault`：水位默认"高于"，闸前/闸后一致，**无需改**
- 告警文案 `content = siteName + metric + ...`，metric 已区分"闸前水位"/"闸后水位"，**无需改**

### 3.3 存量兼容

| 存量行 | 改后行为 |
|---|---|
| 普通水位站 3 行（`zb` 为空） | 通用水位传 `""` → `COALESCE(NULLIF(zb,''),'')=''` 命中 ✓ |
| 闸站 10 行（`up_z`/`down_z`） | 闸前/闸后分别传指标 → 精确命中 ✓ |
| 闸站若存在 `zb` 为空的 `#1#` 行 | 改后不再被闸前/闸后命中，需人工重配（**当前生产无此情况，已核实**） |
| 其它类型（`#2#`/`#3#`/`#4#`）行 | 调用传 `""`，匹配 `zb` 为空 ✓（已核实无 `zb` 非空的雨量/流量/开度行） |

### 3.4 验证方法

1. **渠首进水闸**（只配 `down_z=42.4`）

## 四、对 hltgq-site 的影响

### 4.1 取数逻辑不用改

hltgq-site 的监测数据取数**全部按 `STCD`（水文站号）或 `site`（站点 id）关联，没有一处按 `device` 关联监测表**（2026-10-26 全量核对）：

| 场景 | 关联键 | 拆分后 |
|---|---|---|
| 站点详情-水位 | `river_info."STCD"` | 不变 |
| 站点详情-雨量 | `rain_info."STCD"` | 不变 |
| 站点详情-流量 | `wt_nfo.site` | 不变 |
| 站点详情-闸门开度 | `gate.site` + `gate_no` | 不变 |
| 闸门监测页 | `gate.site` + 站点档案 `epjutj` | 不变 |
| 流量监测页 | `wt_nfo` `COALESCE(stcd, site)` | 不变 |
| 视频巡检 | `video_patrol.channel_code` = 设备 `code` | 不变（视频设备不拆） |

### 4.2 需要跟着变的四处

**① 雨量补偿配置（`t_auto_hltgq_water_rain_adjust`）——必须同批迁移**

该表唯一/匹配键是 `device`，mq 按 `device.id` 匹配补偿值。雨量设备拆出来后，配置行的 `device` 要改指新雨量计设备，否则补偿直接失效（当前只有花凉亭坝上 1 站在用，出厂兜底值 `-34` 也在，但兜底只对 stcd `3206400007` 生效）。

```sql
UPDATE "qixiao-apaas".t_auto_hltgq_water_rain_adjust
   SET device = '<新雨量计id>'
 WHERE device = '<原设备id>';
```

**执行时机**：与 mq 开关切换同一批次。切换后 mq 写入的 `device` 是新雨量计 id，配置表若还是旧 id，补偿会静默失效（不会报错，只是雨量值不再修正）。

**② 告警与工单的 device 展示**

- 历史告警/工单的 `device` 仍指向旧设备 → **旧设备不要删**，前端按 `device` LEFT JOIN 设备名，删除后会显示空
- 新告警挂到传感器设备上 → 展示更准确（"虎形潭渡槽水位计#"而不是"流量计#"）
- 站点详情页工单列表 `LEFT JOIN water_device d ON w.device = d.id`，不受影响

**⚠ 切换瞬间的告警悬挂风险（必须处理）**

mq 的 `AlertService#closeThresholdAlerts`（第 385 行）与 `WorkOrderService#closeThreshold` 都按 `site = ? AND device = ?` 匹配关闭。拆分后 `device` 变了，**切换前已产生、仍处于未确认/已确认状态的阈值告警及对应工单会永远关不掉**：新数据走到新设备，恢复逻辑按新 device 找不到旧行，这些告警会一直挂在未处理列表里。

处理二选一（建议 A）：

- **A（建议）**：`closeThresholdAlerts` / `closeThreshold` 去掉 `device = ?` 条件，只按 `site + content 前缀 + created_by='SYSTEM' + status 白名单` 关闭。阈值配置本身与设备无关（`findThreshold` 注释已写明"阈值按站点×类型(+zb)唯一，同站同指标的全部设备/测点共用一条线"），去掉该条件语义上更正确，且拆分前后都能正常关闭。
- **B（兜底）**：保留逻辑，切换前一次性关闭旧设备下未关闭的阈值告警与工单（页面人工处理或 DBA 执行 UPDATE）。

**③ 设备统计数字会变**

- 设备总数从 465 增加约 45 台（42 台拆开 + 部分站补建）
- 受影响页面：大屏设备数（`DashboardMapper`）、网络设备总览（`NetworkDeviceMapper`）、站点详情设备列表（`StationDetailMapper`）
- 属于预期变化，需提前告知业主"设备数增加是因为按传感器建账，不是新装了设备"

**④ 设备下拉选项**

- 阈值设置页：站点候选按 `epjutj` 判定，**不受影响**；`zb` 指标下拉已支持 `up_z`/`down_z`
- 雨量补偿页：设备下拉 `selectDeviceOptions` 现在只按 `site` 查、不过滤类型，拆后单站设备从 2~3 台变 5~6 台，下拉里会混进水位计/流量计/闸门设备，容易选错。**建议加 `AND type LIKE '%#2#%'`**——这是 hltgq-site 侧唯一建议改的代码；列表回显走 `selectDeviceById` 单条查询，历史记录不受下拉过滤影响。
- 站点详情设备列表：会出现新传感器设备（这是拆分的目的）

### 4.3 阈值设置页无需改动

`ThresholdServiceImpl` 已按「站点 + 类型 + 指标」维护，唯一性判断（`existsSame`）、候选站点（闸站按 gate 表有效数据显示）、指标下拉都已支持 `up_z`/`down_z`。mq 对齐后即闭环。

## 七、联系与核对口径

本文所有数据取自 2026-10-26 对生产库的只读查询，关键口径：

- 监测表与设备的关联键：`river_info.device` / `rain_info.device` / `wt_nfo.device` / `gate.device` = 设备表 `id`（四表均全量填充）
- 视频关联：`video_patrol.channel_code` = 设备表 `code`
- 站点关联：`river_info."STCD"` / `rain_info."STCD"` = 站点档案 `iofhpi`；`wt_nfo.site` / `gate.site` = 站点档案 `id`
- 阈值表：`t_auto_hltgq_water_threshold`，`zvieyb` = 阈值类型，`zb` = 监测指标，`alarmdir` = 方向，`threshold` = 警戒值

如需重新核对，可用以下 SQL（只读）：

```sql
-- 实际采多类数据的设备
WITH wl AS (SELECT device, count(*) c FROM "qixiao-apaas".t_auto_hltgq_water_river_info
            WHERE device IS NOT NULL AND device <> '' GROUP BY 1),
     fl AS (SELECT device, count(*) c FROM "qixiao-apaas"."t_auto_hltgq_water_wt_nfo"
            WHERE device IS NOT NULL AND device <> '' GROUP BY 1),
     rn AS (SELECT device, count(*) c FROM "qixiao-apaas".t_auto_hltgq_water_rain_info
            WHERE device IS NOT NULL AND device <> '' AND deleted IS NOT TRUE GROUP BY 1),
     gt AS (SELECT device, count(*) c FROM "qixiao-apaas"."t_auto_hltgq_water_gate"
            WHERE device IS NOT NULL AND device <> '' GROUP BY 1)
SELECT d.id, d.name, d.type, COALESCE(wl.c,0) wl, COALESCE(fl.c,0) fl,
       COALESCE(rn.c,0) rn, COALESCE(gt.c,0) gt
FROM "qixiao-apaas"."t_auto_hltgq_water_device" d
LEFT JOIN wl ON wl.device = d.id LEFT JOIN fl ON fl.device = d.id
LEFT JOIN rn ON rn.device = d.id LEFT JOIN gt ON gt.device = d.id
WHERE (CASE WHEN COALESCE(wl.c,0)>0 THEN 1 ELSE 0 END
     + CASE WHEN COALESCE(fl.c,0)>0 THEN 1 ELSE 0 END
     + CASE WHEN COALESCE(rn.c,0)>0 THEN 1 ELSE 0 END
     + CASE WHEN COALESCE(gt.c,0)>0 THEN 1 ELSE 0 END) >= 2
ORDER BY d.name;

-- 闸站阈值配置现状
SELECT s.zzkaec, s.epjutj, t.zvieyb, t.zb, t.alarmdir, t.threshold
FROM "qixiao-apaas".t_auto_hltgq_water_threshold t
LEFT JOIN "qixiao-apaas".t_auto_hltgq_5nw74_vnqqef s ON s.id = t.site
ORDER BY s.zzkaec, t.zb;
```
